# システムヘルスチェッカー(総合ミニプロジェクト)

## これまで学んだことの集大成として

ここまでの「01-basics(基礎編、全13章)」と「02-server-engineer-practice(実践編、全5章)」で、変数・関数・配列・オブジェクト・エラー処理・非同期処理・クラス・JSON、そしてNode.jsのコアモジュール(`fs` や `path` など)、CLIツールの作り方、HTTPサーバーの基本といった知識を積み上げてきました。

このディレクトリは、それらすべてを1つの実用的なツールとして組み立てる「総合ミニプロジェクト」です。他の章とは違い、`exercise.js` を埋める形式ではなく、**最初から完成した状態のコード**として用意してあります。まずは実際に動かして体験し、次にコードを1行ずつ読んで「なぜこう書かれているのか」を理解し、最後に自分自身の手で機能を拡張してみる、という3段階で学んでください。

## 仕様(このツールが何をするか)

「システムヘルスチェッカー」は、次のような流れで動くCLI(コマンドラインインターフェース)ツールです。

1. `services.config.json` という設定ファイルを読み込む。ここには「監視したいサービス」の一覧がJSON形式で書かれている
2. 一覧に書かれた各サービスについて、実際に「生きているか(UP)」「死んでいるか(DOWN)」をチェックする
3. チェック結果をターミナルに人間が読みやすい形で表示する
4. 同じ結果を `logs/` ディレクトリの下にログファイルとして書き出す
5. もし1件でもDOWNのサービスがあれば、プロセスの終了コードを `1`(異常終了)にして終わる

これは実際のサーバー運用現場で使われている「死活監視ツール」を、ごく小さく・分かりやすく再現したものです。今回は `type: "file"`(指定したファイルが存在するかどうかを確認する)というチェック種別だけを実装していますが、`services.config.json` の書き方や `checker.js` の設計は、将来「HTTPで実際のURLにアクセスして確認する」「特定のポートが開いているか確認する」といったチェック種別を追加できるように意識してあります(詳しくは下の「発展課題」を参照してください)。

## ディレクトリ構成の説明

```
03-capstone/system-health-checker/
├── README.md              このファイルです
├── services.config.json   チェック対象のサービス一覧(設定ファイル)
├── src/
│   ├── checker.js          「チェックする」処理だけを持つコアロジック
│   ├── logger.js           「結果を整形してログファイルに書き出す」処理だけを持つコアロジック
│   └── cli.js               実行の入り口(エントリーポイント)。上記2つを呼び出して進行させる
├── test/
│   └── checker.test.js     checker.js と logger.js の自動テスト
└── logs/
    └── .gitkeep             ログの出力先ディレクトリ(実行するとここにログファイルが増えていく)
```

ポイントは、**「チェックする処理(checker.js)」「記録する処理(logger.js)」「進行を取りまとめる処理(cli.js)」を、それぞれ別のファイルに分けている**ことです。こうしておくと、

- `checker.js` と `logger.js` は「入力を渡すと決まった値を返すだけ」の純粋な関数の集まりなので、`test/checker.test.js` から直接呼び出して自動テストできる
- `cli.js` は「設定を読む → チェックする → 表示する → 保存する」という流れをつなぐだけの薄い層になり、見通しがよくなる

という利点が生まれます。これは 02-server-engineer-practice/02-cli-tool で学んだ「コアロジックとCLIの分離」を、より本格的な複数ファイル構成に発展させたものです。

## 実行方法

リポジトリのルートディレクトリで、次のコマンドを実行してください。

```bash
node 03-capstone/system-health-checker/src/cli.js
```

`services.config.json` にはあらかじめ、実在するファイル(`README.md` など)と、わざと存在しないパス(`does-not-exist.txt` など)の両方をサンプルとして登録してあります。そのため、実行すると次のように **UPとDOWNの両方が実際に表示される**はずです(日時の部分は実行するたびに変わります)。

```
=== システムヘルスチェック ===
[UP] readme-file (checked at 2026-08-30T12:35:10.123Z)
[UP] config-file-itself (checked at 2026-08-30T12:35:10.123Z)
[NG] missing-config-file (checked at 2026-08-30T12:35:10.123Z)
[NG] phantom-log-file (checked at 2026-08-30T12:35:10.123Z)
--- 合計: 4件中 UP=2 / DOWN=2 ---
ログファイルを書き出しました: /path/to/03-capstone/system-health-checker/logs/health-check-2026-08-30T12-35-10-130Z.log
```

`[UP]` は「正常(生きている)」、`[NG]` は「異常(死んでいる)」を表す文字ラベルです。絵文字ではなく文字だけで状態を伝えているのは、ターミナル環境によっては絵文字が正しく表示されないことがあり、サーバー運用の現場では「文字だけで確実に状態が伝わること」が重視されるためです。

DOWNのサービスが1件でもあると、このコマンドの終了コードは `1` になります。直後に次のコマンドを実行すると、終了コードを確認できます。

```bash
echo $?
```

## テストの実行方法

```bash
node --test 03-capstone/system-health-checker/test/checker.test.js
```

`test/checker.test.js` の中では、`checkService` / `checkAll`(checker.js側)と `formatSummaryLine` / `buildLogContent` / `writeLogFile`(logger.js側)のそれぞれについて、正常系(期待通り動くケース)・境界値(空配列など)・異常系(未対応のtypeを渡した場合)をテストしています。すべて緑(成功)になれば、このツールが仕様通りに動作していることが確認できます。

## 発展課題(腕試し)

このツールは、あえて `type: "file"` だけに対応した最小限の実装にとどめてあります。理由は、ネットワークに依存する機能(実際のURLに接続を試みる、実際のサーバーのポートに接続してみる、など)は、実行する環境によって結果が変わってしまい、`node --test` を誰の環境で実行しても同じ結果になるとは限らないためです。そのため本プロジェクトでは、まず「ファイルの存在確認」という環境に依存しないチェックだけを完成形として実装し、ネットワークが絡む部分は皆さん自身の「腕試し」として残しています。

以下の課題に挑戦してみてください。

1. **`type: "http"` チェックの追加**: `checkService` に `type === "http"` の分岐を追加し、Node.js 18以降に標準搭載されている `fetch()` を使って、`target` に書かれたURLへリクエストを送り、レスポンスのステータスコードが200番台なら `"UP"`、それ以外やエラー(接続できないなど)なら `"DOWN"` を返すようにしてみましょう。`fetch()` は非同期関数(Promiseを返す関数)なので、`checkService` と `checkAll` を `async function` に書き換え、呼び出す側(`cli.js`)も `await` を使うように直す必要がある点に注意してください。
2. **タイムアウト処理の追加**: 課題1に取り組んだ場合、応答が返ってこないサーバーをチェックすると、いつまでも待ち続けてしまう問題が起きます。`AbortController`(Node.js標準の、処理を途中で中断させるための仕組み)を使って、「3秒待っても応答がなければDOWN扱いにする」といったタイムアウト処理を実装してみましょう。
3. **`type: "port"` チェックの追加**: `node:net` モジュールの `net.createConnection` を使い、「指定したホスト・ポート番号に接続できるかどうか」を確認するチェック種別を追加してみましょう。データベースサーバーのポートが開いているかを確認する、といった実務でよくある監視方法を模したものです。

これらの課題に取り組む際は、`services.config.json` に新しい `type` のサービスを追加し、`test/checker.test.js` にならって自分でテストコードも書いてみると、より理解が深まります(テスト対象のサーバーを用意する必要がある場合は、`node:http` で簡易サーバーをテストの中で一時的に立ち上げる、という方法もあります)。

## この章がサーバー構築エンジニア志望者にとってなぜ重要か

サーバー構築エンジニア(インフラエンジニア)の実務では、「サーバーやサービスが正常に動き続けているかを常に監視し、異常があればすぐに気づけるようにする」ことが基本業務の1つです。これを死活監視(せいかつかんし、"is it alive?" を確認する監視)と呼びます。実際の現場では Zabbix・Prometheus・Datadog といった専用の監視ツールを使うことが多いですが、それらのツールも突き詰めれば「対象をチェックする → 結果を記録する → 異常なら通知する」という、このミニプロジェクトと同じ骨組みで動いています。

さらに、このプロジェクトで扱った「設定ファイル(JSON)を読み込んで動作を変える」「結果をログファイルとして残す」「異常時は終了コードで機械的に異常を伝える」という3つの要素は、監視ツールに限らず、デプロイスクリプトやバックアップスクリプトなど、サーバー運用の自動化(オートメーション)全般に共通する基本パターンです。手作業に頼らず、こうした小さなツールを自分で組み立てられることこそが、インフラエンジニアに求められる実践的なスキルの土台になります。
